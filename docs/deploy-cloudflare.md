# 本番環境の構築手順(Cloudflare Pages + WAF)

ホスティングは Cloudflare Pages、アクセス制限は Cloudflare WAF のカスタムルールで、許可したIPアドレス以外をブロックする。
この方式に決めた理由は「ホスティング先とアクセス制限の決定」の記録を参照。

- PDFはブラウザの中だけで処理し、サーバーには何も送らない。アクセス制限の役割は「社外の人にアプリを開かせない」こと
- 作業はすべて Cloudflare のダッシュボードと GitHub の設定で行う。アカウント・ドメインの権限がある人が作業する

## このアプリの設定値

| 項目 | 値 |
|---|---|
| ドメイン | `pdfcheck-tool.com`(Cloudflare で購入・管理) |
| Pages のプロジェクト名 | `pdf-check-tool`(`https://pdf-check-tool.pages.dev`) |
| 許可するIPアドレス | 未定(決まったら 5 のリストに入れる) |

以下の手順の `<独自ドメイン>` は `pdfcheck-tool.com`、`<プロジェクト名>` は `pdf-check-tool` に読み替える。

## 全体の流れ

| # | 作業 | いつ |
|---|---|---|
| 1 | ドメインを Cloudflare に登録する | 最初に1回 |
| 2 | Pages のプロジェクトを作り、デプロイする | 最初に1回(以降は自動) |
| 3 | 独自ドメインを Pages に割り当てる | 最初に1回 |
| 4 | `*.pages.dev` の URL を閉じる | 最初に1回 |
| 5 | 許可するIPアドレスのリストを作る | **IPが決まってから**(あとから何度でも変えられる) |
| 6 | WAF のカスタムルールで、リストにないIPをブロックする | リストを作ったら |
| 7 | 動作を確認する | 毎回の変更後 |

---

## 1. ドメインを Cloudflare に登録する

WAF のルールは、Cloudflare に登録したドメイン(ゾーン)に対して効く。

1. Cloudflare のダッシュボードで「ドメインを追加」から、使うドメインを登録する(無料プランでよい)
2. 表示されたネームサーバーに、ドメインの登録業者側で切り替える
3. ドメインの状態が「有効」になるまで待つ

会社のドメインのサブドメイン(例: `pdf.example.co.jp`)だけを使いたい場合も、親のドメインを Cloudflare で管理している必要がある。
社内のDNSを動かせない場合は、情報システムの担当者と相談する。

## 2. Pages のプロジェクトを作り、デプロイする

デプロイの方法は2つある。**A(GitHub Actions からアップロード)をおすすめする。**
CI のチェック(Lint・テスト・外部URLのチェック・E2E)が全部通ったときだけデプロイでき、プレビュー用の URL も作られないため。

### A. GitHub Actions からアップロードする(おすすめ)

1. Cloudflare のダッシュボードの「Workers & Pages」で「Create application」を押し、画面の一番下の
   「Continue to Pages」から、Pages のプロジェクトを「Upload assets」(直接アップロード)で作る。
   プロジェクト名は URL の一部になる(`<プロジェクト名>.pages.dev`)。
   ※ 上に並ぶ「Connect GitHub」「Upload your static files」は Workers として作られるので選ばない
2. Cloudflare で API トークンを作る。権限は「アカウント > Cloudflare Pages > 編集」だけにする
3. GitHub のリポジトリの「Settings > Secrets and variables > Actions」に、次を登録する
   - 「Secrets」タブ
     - `CLOUDFLARE_API_TOKEN`: 2 で作ったトークン
     - `CLOUDFLARE_ACCOUNT_ID`: Cloudflare のアカウント ID(「Workers & Pages」の画面の右側に表示される)
   - 「Variables」タブ
     - `CLOUDFLARE_PAGES_PROJECT`: 1 で決めたプロジェクト名
4. これで、main にpushして CI のチェックがすべて通るたびに、自動でデプロイされる(`.github/workflows/ci.yml` の `deploy`)。
   - デプロイするのは、チェックを通ったときにビルドした `dist/` そのもの
   - `CLOUDFLARE_PAGES_PROJECT` を登録するまでは、デプロイの処理は動かない
   - GitHub の「Actions」タブで、`deploy` が成功したかを確かめられる

最初の1回は、ダッシュボードから `dist/` をアップロードしてプロジェクトを作ってもよい(`npm run build` で作られる)。

### B. Cloudflare に GitHub のリポジトリを連携する

1. 「Workers & Pages」で、Pages のプロジェクトを「Git に接続」で作り、このリポジトリを選ぶ
2. ビルドの設定: ビルドコマンド `npm run build`、出力ディレクトリ `dist`
3. 「Settings > Builds > Branch control」で、プレビュー用のデプロイを「なし」にする
   (既定では、main 以外のブランチをpushするたびに、公開された URL でプレビューが作られる)

この方法では、CI のチェックの結果を待たずにデプロイされる。

### デプロイされるもの

- `dist/` の静的ファイルだけ。サーバー側のプログラム(Pages Functions)は使わない
- `dist/_headers` は、ビルドで自動的に作られる(`vite-plugins/security-headers.ts`)。
  Cloudflare Pages はこのファイルを読み、すべてのパスの応答に CSP のヘッダーを付ける

## 3. 独自ドメインを Pages に割り当てる

1. Pages のプロジェクトの「カスタムドメイン」で、1 のドメイン(またはサブドメイン)を追加する
2. DNS のレコードは Cloudflare が自動で作る。証明書の発行が終わるまで数分待つ
3. ブラウザで独自ドメインを開き、アプリが表示されることを確かめる

## 4. `*.pages.dev` の URL を閉じる

WAF のルールは独自ドメインにしか効かない。`<プロジェクト名>.pages.dev` は誰でも開けてしまうので、閉じておく。

1. 本番の URL: 「Bulk Redirects」で、`<プロジェクト名>.pages.dev` から独自ドメインへ転送する
   1. リダイレクトのリストを作り、転送元に `<プロジェクト名>.pages.dev`、転送先に `https://<独自ドメイン>`、ステータスに 301 を入れる。
      「クエリ文字列を保持」「サブパスを一致させる」「パスの接尾辞を保持」「サブドメインを含める」を有効にする
   2. そのリストを使うリダイレクトのルールを作り、有効にする
   3. `<プロジェクト名>.pages.dev` を開き、独自ドメインに転送されることを確かめる(転送先で WAF が効く)
2. プレビューの URL(`<ハッシュ>.<プロジェクト名>.pages.dev`):
   - 2 の A の方法なら、main 以外はデプロイしないので作られない
   - 2 の B の方法なら、Branch control でプレビューを止めたうえで、念のため「Settings > General > Enable access policy」
     で Cloudflare Access をかける(Access は 50 人まで無料)

## 5. 許可するIPアドレスのリストを作る(あとから設定・変更できる)

**許可するIPアドレスは、あとから何度でも追加・削除できる。** IPを「リスト」にまとめ、6 のルールからリストを参照する形にしておけば、
変更のときはリストだけを直せばよく、ルールには触らない。変更は数十秒で反映される。

1. Cloudflare のダッシュボードの「Manage Account > Configurations > Lists」で、IP のリストを作る
   - 名前の例: `allowed_ips`(英小文字・数字・`_` だけ。ルールの中で `$allowed_ips` として参照する)
   - 種類: IP
2. 許可するIPアドレスを追加する。1件ずつのほか、範囲(CIDR。例: `203.0.113.0/24`)でも書ける。
   各IPに「本社」「〇〇営業所」のような説明を付けておくと、あとで見直しやすい
3. あとから変えるときは、このリストの項目を足す・消すだけでよい

無料プランでは、カスタムのリストは **1つ**、項目は全部で **10,000件** まで作れる(このアプリには十分)。

**IPがまだ決まっていないとき:**

- 6 のルールは作っておき、**無効のまま**にしておく。リストが空のままルールを有効にすると、全員がブロックされる
- その間は、アプリの URL を関係者以外に知らせない。サーバーには個人情報が何もないので、URL が知られても
  漏れる情報はないが、社外の人にツールを使わせない、という目的は果たせない
- 先に作業者自身のIPだけを入れて有効にしておき、あとで本番のIPを足す方法もある

**IPアドレスについて確かめておくこと:**

- 利用者がオフィスの**固定IP**から使うこと。プロバイダーから割り当てられるIPが変わる回線では、この方式は使えない
- 調べ方: オフィスのネットワークから、Cloudflare の `https://<独自ドメイン>/cdn-cgi/trace` を開き、`ip=` の行を見る
  (独自ドメインの割り当てが終わってから使える)
- 在宅勤務や外出先から使う人がいる場合は、VPN で社内を経由するか、Cloudflare Access(メールや SSO で認証)に切り替える

## 6. WAF のカスタムルールで、リストにないIPをブロックする

1. 独自ドメインの「Security > WAF > Custom rules」で、ルールを作る
   - ルール名: `許可したIP以外をブロック`
   - 式(「式を編集」を選んで直接書く):

     ```
     (http.host eq "<独自ドメイン>" and not ip.src in $allowed_ips)
     ```

   - アクション: ブロック
2. IP のリストを作り終えたら、ルールを有効にする
3. 無料プランのカスタムルールは5つまで。このルール1つで足りる

`http.host` で絞っているのは、同じドメインのほかのサブドメインに影響しないようにするため。
ドメイン全体をこのアプリだけに使うなら、`not ip.src in $allowed_ips` だけでもよい。

## 7. 動作を確認する

| 確認すること | 方法 | 期待する結果 |
|---|---|---|
| 許可したIPから開ける | オフィスのネットワークから独自ドメインを開く | アプリが表示される |
| 許可していないIPからは開けない | スマートフォンのモバイル回線(Wi-Fi を切る)から開く | Cloudflare のブロック画面(403)になる |
| `*.pages.dev` が閉じている | `<プロジェクト名>.pages.dev` を開く | 独自ドメインに転送され、許可していないIPならブロックされる |
| CSP のヘッダーが付いている | ブラウザの開発者ツールの「ネットワーク」で、トップページの応答ヘッダーを見る | `Content-Security-Policy` がある |
| アプリが動く | ダミーPDF(`samples/`)を開く | テキストPDFもスキャンPDF(OCR)も、値が抽出される |

WAF の「Security > Events」で、ブロックしたアクセスの記録(IP・日時)を見られる。

## まだ足りないもの

- CSP 以外のセキュリティ関連のヘッダー(`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`、
  `Permissions-Policy` でカメラ・マイク・位置情報などを無効にする)を、`vite-plugins/security-headers.ts` が作る
  `dist/_headers` に足す必要がある
