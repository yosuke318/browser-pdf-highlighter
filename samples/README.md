# ダミーサンプルPDF

開発と回帰テストに使うダミーのPDF。人物・会社・自治体・銀行はすべて架空で、電話番号は実在しない `000` 始まりにしている。

`scripts/generate-samples/` のスクリプトで生成しているので、直接編集しない。

```bash
npm run samples        # 生成(Google Chrome が必要)
npm run samples:check  # pdf.js で読んで、ページの種類が manifest.json と合っているか確認
```

## 内容

| ディレクトリ | 書類 | 発行元(架空) | 記入 | スキャンの再現 |
|---|---|---|---|---|
| `withholding-slip/` | 源泉徴収票(令和7年分) | 株式会社サンプル商事 | 活字 | A4用紙の上部に置いてスキャン |
| `tax-certificate/` | 課税(所得)証明書(令和8年度) | 見本市 | 活字 | 偽造防止の地紋(「複写」の文字)と公印の重なり |
| `resident-tax-notice/` | 住民税決定通知書(特別徴収・納税義務者用、令和8年度) | 見本市 | 活字 | 通常のスキャン |
| `tax-return/` | 確定申告書 第一表(令和7年分) | 本人作成 | 活字(マス目に1桁ずつ) | 通常のスキャン |
| `home-loan-application/` | 住宅ローン借入申込書 | サンプル銀行 | 手書き風 | 通常のスキャン |
| `rental-application/` | 入居申込書(賃貸) | 見本不動産管理 | 手書き風 | FAX受信(縦の解像度が半分、白黒2値、点状のノイズ) |

各ディレクトリのファイル:

- `text.pdf` … テキストPDF(文字データあり)。OCRの結果と比べる基準にも使える
- `scan.pdf` … スキャンPDF(画像のみ、200dpi相当、傾き・ノイズあり)
- `expected.json` … PDFに書かれている値(正解データ)。形式は `schema/extraction-fields.json` の抽出項目の定義に合わせている

`pdf-kinds/` はテキストPDFかスキャンPDFかの自動判別をテストするためのもの:

- `searchable.pdf` … 透明テキスト付きPDF(サーチャブルPDF)。源泉徴収票のスキャン画像の上に、見えない文字(テキスト描画モード3)を重ねたもの
- `mixed.pdf` … 1ページ目が確定申告書のテキストPDF、2ページ目が源泉徴収票のスキャンPDF

`manifest.json` に、全ファイルのページごとの種類(`text` / `scanned` / `searchable`)をまとめている。

## リグレッションテスト

`npm test` で、ダミーPDFを使った次のテストも走る(`src/regression/`)。CIでも毎回実行する。

| テスト | 確かめること | 記録 |
|---|---|---|
| `text-coverage.test.ts` | テキストPDFから取り出した文字の中に、正解データの各値が見つかるか(文字の取り出しと正規化の確認) | `src/regression/__snapshots__/text-coverage.json` |
| `extraction.test.ts`(テキストPDF) | 書類の抽出処理(`src/extract/extractors.ts`)で抽出した値が、正解データと一致するか | `src/regression/__snapshots__/extraction/` |
| `extraction.test.ts`(スキャンPDF) | OCR してから抽出し、正しく抽出できた項目の数が基準を下回らないか | `src/regression/__snapshots__/ocr-baseline.json` |

- テキストPDFは、記録と結果が違うと失敗する。値が見つからなくなった(悪くなった)ときだけでなく、見つかるようになった(良くなった)ときも失敗するので、結果を確かめてから `npx vitest run src/regression -u` で記録を更新してコミットする
- テキストPDFの抽出処理は、誤った値や定義にない項目を1つでも返すと失敗する。抽出できなかった項目は失敗にせず、記録に残す
- スキャンPDFは、OCR の文字の読み違い(「郎」→「朗」など)が避けられないので、誤った値があっても失敗にしない。正しく抽出できた項目の数が `ocr-baseline.json` の基準を下回ると失敗する。OCR の結果は実行する環境でわずかに変わることがあるので、基準は手元で取れた数より1つ少なくしている。精度を上げたら、結果を確かめてから基準を上げる
- 手書き風の書類(住宅ローン申込書・入居申込書)は、OCR ではほとんど読めない前提(特に FAX の入居申込書)。基準も低い
- 抽出処理を登録していない書類は「未実装(todo)」と表示される
- 今の記録で見つからない値と理由:
  - 住民税決定通知書の `incomeYear`(対象年): 書類には「令和8年度」しか書かれておらず、年度から計算する値のため
  - 住宅ローン申込書の `birthDate`: 元号を「昭和・平成」の選択肢に丸を付けて選ぶ様式で、丸は図形なので文字からは元号が分からないため

## 実データの扱い

**実在の書類(マスク済みのものを含む)は、リポジトリに入れない。** テスト・コメント・コミットメッセージ・Issue・PRにも、実在の人物の情報を書かない。

- 手元で実データを試すときは `local-samples/` に置く。このディレクトリは `.gitignore` で除外している
- `npm run check:files`(CIでも実行)が、`samples/` の外にあるPDF・画像と、`manifest.json` に載っていないPDFを見つけると失敗する
- ダミーPDFを増やすときは、`scripts/generate-samples/` で生成し、`manifest.json` と `expected.json` を合わせて更新する。人物・会社などは「見本県」「サンプル商事」のように架空と分かる名前にし、電話番号は `000` 始まりにする
- 実データで見つかった様式の特徴(欄の名前・並び・書き方)は、個人情報を含めずにダミーのテンプレートへ反映する

## 注意点

- **手書きは本物よりかなり読みやすい。** 丸ゴシック体の文字を1文字ずつ傾けて手書き風にしているだけなので、OCRで読めても本物の手書きが読めるとは限らない。手書きの精度は、マスク済みの実物で確かめる必要がある
- **様式は簡略版。** 欄の名前(ラベル文言)は実物に合わせているが、レイアウト・欄の数・欄番号は実物と異なる
- **文字化けしたテキストPDFのサンプルはない。** 意図的に作るのが難しいため、実物で見つかったら追加する
- **テキストPDFから取り出した漢字の一部が「康熙部首」になる。** たとえば「支」「見」「民」が `⽀`(U+2F40)`⾒`(U+2F92)`⺠`(U+2EA0)として取り出される(Chromeとヒラギノフォントで作ったPDFで起きる。Macで作られたPDFでもよくある)。抽出時の正規化で通常の漢字に戻す必要がある
